# Iprix's Spells — Engineering Roadmap & Implementation Specification

## 1. Project Vision

Iprix's Spells is intended to become a comprehensive personal web application: a centralized place for practically everything I might need throughout my day.

It should combine productivity tools, file management, utilities, communication, creative tools, and tabletop RPG functionality into one coherent application.

The goal is not simply to accumulate features. The goal is to build a polished, reliable, interconnected ecosystem in which different tools work together naturally.

### Core objectives

1. **Comprehensive functionality:** Provide a broad collection of useful tools without requiring external websites or applications for everyday tasks.
2. **Integration:** Tools should be able to exchange files, data, and information where appropriate.
3. **Excellent UX:** The application should feel like one unified product rather than a collection of disconnected HTML pages.
4. **Performance:** Keep the Raspberry Pi 5 responsive, even when multiple people are using the application.
5. **Privacy:** Prefer browser-side processing and minimize unnecessary server-side data collection.
6. **Reliability:** User data must be protected against accidental deletion, corruption, and unexpected server restarts.
7. **Extensibility:** New tools should be straightforward to add without requiring architectural changes throughout the application.

---

# 2. Architectural Constraints

These constraints are mandatory when implementing new functionality.

## 2.1 Hardware

The application runs on a Raspberry Pi 5.

The server should remain lightweight and should not become the bottleneck as the application grows.

### Computing strategy

Use the browser for computation whenever practical.

**Frontend responsibilities:**
- Image manipulation and conversion using browser APIs.
- Text manipulation and analysis.
- Calculations and mathematical operations.
- Rendering and interactive visualizations.
- Drawing and image editing.
- File previews and lightweight document processing.
- Local state management.
- Interactive tabletop map rendering.
- Validation that can safely happen client-side.

**Backend responsibilities:**
- Authentication and authorization.
- Persistent data storage.
- File uploads and downloads.
- Database operations.
- Synchronization between users.
- Permission enforcement.
- Operations requiring server-side libraries or filesystem access.
- Lightweight API orchestration.

### Performance rules

- Do not transfer large files into Python memory unnecessarily.
- Stream uploads and downloads.
- Avoid loading entire files into memory when processing can be done in chunks.
- Avoid expensive computations inside Flask request handlers.
- Do not introduce heavyweight dependencies without a demonstrated requirement.
- Avoid unnecessary background workers and continuously running services.
- Use browser Web Workers for CPU-intensive client-side tasks.
- Load expensive JavaScript modules only when their functionality is needed.
- Avoid unnecessary API calls and repeated database queries.
- Prefer native browser functionality over large JavaScript libraries where practical.
- Make performance-sensitive operations cancellable.

### Important distinction

Browser-side processing must never replace security validation.

Client-side validation is for UX. All operations that affect permissions, persistence, or server resources must be validated by the backend.

## 2.2 Existing Architecture

Preserve the existing Flask monolith and blueprint architecture unless there is a compelling technical reason to change it.

Current structure:

```text
.
├── app.py
├── auth.py
├── board.py
├── chat.py
├── storage.py
├── set_password.py
├── login.html
├── pages/
├── processing/
├── rules/
├── shared/
├── images/
└── data/
```

Keep new functionality consistent with the existing architecture.

Guidelines:
- Keep unrelated functionality separated into dedicated modules.
- Reuse existing authentication and authorization mechanisms.
- Reuse existing shared CSS and JavaScript components.
- Avoid duplicated implementations of common functionality.
- Keep API contracts consistent.
- Avoid unnecessary abstractions and complicated design patterns.
- Keep the application maintainable by a single developer.

Do not introduce microservices.

# 4. P0 — Security, Reliability & Infrastructure

These improvements should come before substantial feature expansion.

## 4.1 Authentication and Authorization Audit

**Objective:** Ensure that every protected operation is properly authenticated and authorized.

Inspect:
- All Flask routes.
- All API endpoints.
- Blueprint-level authentication.
- DM-specific authorization.
- Campaign and player permissions.
- File download and deletion permissions.
- Direct access to static or uploaded files.
- Session invalidation.

Potential improvements:
- Centralized permission-checking decorators.
- CSRF protection for state-changing requests.
- Secure session cookie settings.
- Session rotation after login.
- Consistent permission checks across frontend and backend.
- Protection against path traversal.
- Upload type and size validation.
- Security headers.
- Rate limiting for sensitive endpoints.
- Careful handling of reverse-proxy headers.

The frontend must never be trusted to enforce permissions.

**Acceptance criteria:**
- Unauthenticated users cannot access protected resources.
- Players cannot perform DM-only operations.
- API endpoints enforce the same permissions as their corresponding interfaces.
- File identifiers cannot be manipulated to access unauthorized files.
- Authentication cannot be bypassed by accessing an endpoint directly.

## 4.2 Data Integrity and Backup System

**Objective:** Protect all user-generated data.

Important data includes:
- Storage files.
- SQLite databases.
- Campaign data.
- Character sheets.
- Map data.
- Authentication secrets.
- Application configuration.

Potential improvements:
- Automatic database backups.
- Configurable backup schedules.
- Backup rotation.
- Backup integrity verification.
- Database integrity checks.
- Recovery instructions.
- Atomic file operations.
- Safe SQLite transactions.
- Schema migrations.

Keep backups separate from the primary data directory. A backup stored only on the same Raspberry Pi does not provide adequate protection against hardware failure.

**Acceptance criteria:**
- Important data can be restored after an application restart.
- A backup can be restored successfully in a test environment.
- Interrupted uploads do not create corrupt files.
- Interrupted database operations do not leave inconsistent data.
- Database migrations preserve existing user data.

## 4.3 Resource and Error Management

**Objective:** Make the application predictable under failure and resource pressure.

Potential improvements:
- Consistent API error responses.
- Request size limits.
- Storage quotas.
- Upload cleanup.
- Expiration of temporary files.
- Better exception logging.
- Disk-space monitoring.
- Basic server health endpoint.
- Database connection management.
- Protection against accidental resource-intensive operations.

Add an administrative diagnostics page displaying:
- Server availability.
- Application version.
- Available disk space.
- Storage usage.
- Database status.
- Active sessions, where practical.
- Recent application errors.

Avoid exposing sensitive server information to unauthenticated visitors.

# 7. P1 — Cross-Tool Integration

**Objective:** Make the tools work together rather than exist independently.

This is one of the highest-value improvements to the overall product.

## 7.1 Unified File Interface

Build a reusable file selection and file-opening interface.

Tools should be able to:
- Open files from storage.
- Upload files directly.
- Receive files from other tools.
- Export results to storage.
- Download processed files.

Example:

```text
Cloud Storage
    │
    ├── Open in Image Editor
    ├── Open in PDF Viewer
    ├── Open in Text Tools
    ├── Open in File Converter
    └── Open in Spreadsheet Viewer
```

## 7.2 Processing Pipeline

Allow users to perform multiple operations on the same file without repeatedly downloading and uploading it.

Example:

```text
Upload PDF
    ↓
Extract Text
    ↓
Edit Extracted Text
    ↓
Generate New Document
    ↓
Save to Cloud Storage
```

Another example:

```text
Upload Image
    ↓
Resize
    ↓
Convert to WebP
    ↓
Compress
    ↓
Save Result
```

Use browser-side processing by default.

Do not introduce a complicated server-side workflow engine unless the actual use cases justify it.

## 7.3 Shared File Context

Create a consistent way for tools to receive and return files.

Potential capabilities:
- File object references.
- MIME type information.
- File metadata.
- Original filenames.
- Exported Blob objects.
- Storage references.

Avoid duplicating large file data between tools or putting it in URL query parameters.

# 14. Implementation Protocol for the AI Agent

This section is mandatory.

The roadmap is not an instruction to implement every feature in one massive operation.

The agent should work incrementally and maintain a clear understanding of the existing codebase.

## Phase 1 — Repository Audit

Before making changes:

1. Inspect the complete repository.
2. Read the existing documentation.
3. Inspect the Flask routes and blueprints.
4. Understand authentication and authorization.
5. Understand frontend architecture.
6. Understand the SQLite databases and file storage.
7. Identify existing shared components.
8. Identify duplicated implementations.
9. Inspect existing tests.
10. Run the application and existing tests where practical.

Produce an audit containing:

- Existing functionality.
- Partially implemented functionality.
- Missing functionality.
- Architectural weaknesses.
- Security concerns.
- Performance bottlenecks.
- Technical debt.
- Existing conventions that should be preserved.

Do not assume something is missing simply because it is absent from this roadmap.

Do not rewrite existing systems before understanding why they were implemented the way they were.

## Phase 2 — Implementation Planning

Convert the relevant roadmap items into independent implementation tasks.

Each task must contain:

### Task template

```markdown
# Task: [Name]

## Objective
What are we trying to achieve?

## Current implementation
What currently exists?

## Problem
What needs improvement?

## Proposed solution
How should it be implemented?

## Relevant files
Which files are likely to be affected?

## Dependencies
What must exist before implementation?

## Acceptance criteria
What must work for the task to be considered complete?

## Tests
What should be tested?

## Performance considerations
How does the implementation affect the Raspberry Pi?

## Security considerations
What data and permissions are involved?

## Documentation
What documentation needs updating?
```

Tasks should be small enough to implement, test, and review independently.

## Phase 3 — Implementation

For each task:

1. Inspect the relevant code.
2. Understand the existing behavior.
3. Identify the smallest sensible implementation.
4. Implement the feature.
5. Test the functionality.
6. Test edge cases.
7. Check for regressions.
8. Review the resulting changes.
9. Update documentation.
10. Report the outcome.

Do not implement unrelated improvements during a task merely because they are nearby in the code.

Prefer small, focused changes over large rewrites.

## Phase 4 — Verification

A task is not complete merely because the code has been written.

Verify:
- The feature works.
- Existing functionality still works.
- Permissions are enforced.
- Errors are handled.
- Data persists correctly.
- Refreshing the page does not break functionality.
- Mobile layouts remain usable where relevant.
- The Pi is not unnecessarily burdened.
- No unnecessary dependencies were introduced.

For new APIs, test both authorized and unauthorized requests.

For data modifications, test failure and interruption scenarios where practical.

## Phase 5 — Documentation

Update the appropriate documentation whenever implementation changes the application.

Document:
- New functionality.
- Changed APIs.
- Data structures.
- New dependencies.
- Configuration changes.
- Migration procedures.
- Important architectural decisions.

Keep the Obsidian project documentation synchronized with the actual code.

Do not document functionality that has not been implemented.

# 15. Working Rules

The following rules are especially important.

### Do

- Inspect before modifying.
- Prefer existing implementations when they are appropriate.
- Implement features incrementally.
- Keep changes focused.
- Preserve backward compatibility where possible.
- Test actual behavior.
- Verify data integrity.
- Reuse shared components.
- Keep the Pi lightweight.
- Explain significant architectural decisions.
- Maintain a record of completed work.

### Do not

- Rewrite the entire application.
- Introduce microservices.
- Add large dependencies without justification.
- Move every operation to the backend.
- Make unnecessary database migrations.
- Delete existing features to simplify implementation.
- Hardcode user preferences.
- Trust frontend permission checks.
- Ignore errors.
- Mark untested functionality as complete.
- Make destructive changes without a verified backup.

### When encountering uncertainty

Do not invent assumptions about how the application works.

Inspect the relevant code first.

When multiple implementations are reasonable:
1. Prefer the simplest maintainable solution.
2. Consider Raspberry Pi resource consumption.
3. Consider future extensibility.
4. Consider compatibility with existing functionality.
5. Document meaningful trade-offs.

If an existing architectural decision creates a problem, explain the problem and propose a targeted solution rather than silently replacing the architecture.

# 17. Definition of Done

Iprix's Spells should progressively reach the following state:

- Every tool is accessible through a unified interface.
- The application has a consistent design system.
- Files can move naturally between tools.
